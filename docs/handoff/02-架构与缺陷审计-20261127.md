### 一个反直觉的好消息

所以"bug 很多"的根源**不在后端错误处理**，而在：
1. 前端状态机复杂度（App.tsx 28 个 effect 的时序耦合）
2. 播放器与主窗的跨进程协调（mpv 是独立顶层窗口）
3. 数据层的历史遗留（迁移不彻底导致的重复与幽灵行）

## 2. 卡顿根因链

实测与代码核对，卡顿由四层叠加，**不是单一原因**：

### 2.1 扫描是全库递归，与物理分夹无关

`lib.rs` 的扫描走全库递归。物理上分成 `0-199`/`200-399`… 十个区间夹，只让资源管理器好翻，对影匣自身的扫描成本**零收益**。这是"分文件夹防卡顿"这个假设失效的根本原因——扫描器看到的是 1946 个文件，不管它们在一个夹还是十个夹。

### 2.2 封面懒抽帧的排队雪崩

打开大夹首屏取 48 张卡片，每张进视口才请求中帧封面。前端限 2 路并发（`cover.ts`），后端 `COVER_GATE` 串行（`lib.rs`）。视口没填满时 `IntersectionObserver` 会连续翻页，抽帧任务瞬间堆积。

接触表覆盖率只有 **698 / 1946（36%）**，剩下三分之二首次打开必须现场抽帧。

### 2.3 无虚拟列表时 DOM 全量堆积

已做窗口化渲染（0.1.25），但文件夹卡的 2×2 拼贴仍是 N+1 查询 + 逐个 `is_file()` 检查（`db.rs`），每次进入文件夹列表都要跑。

### 2.4 数据库无内容去重，行数虚高

1946 条活跃记录里有 39 组是同一文件在两个夹各存一份。虽然不影响查询速度（有索引），但直接放大了扫描、抽帧、首屏渲染的全部工作量。

## 3. 数据层缺陷（均可量化）

### 3.1 真重复：39 组，可回收 23.2GB

活跃记录中，同一 `file_name` + 同一 `size_bytes` 在两个不同区间夹各存在一份，且**物理上两份都真实存在**。

最典型：`Flim13的大合集`（10.9GB）同时存在于 `1600-1799` 和 `1800-1999`。

成因推测：手工复制/移动过文件，或导入器在旧根与新根之间重复登记。当前扫描按路径去重（`path` + `entry_index` 唯一），路径不同就认作不同视频，**不看内容**。

### 3.2 回收站幽灵行：203 条，账面 113.5GB

`trashed=1` 的记录共 203 条，`size_bytes` 合计约 113.5GB，但**磁盘上文件只剩两个测试视频**。删文件没清库。

后果：统计面板显示的"回收站占用"是假的，用户以为还有 113GB 可清，实际是 0。

### 3.3 区间夹改名遗留：`1-199` → `0-199`

夹命名从 `1-199` 改成 `0-199` 时，**旧记录没迁**：
- `1-199` 还挂着 **198 条**（全部 `trashed=1`）
- `0-199` 是新的 200 条

这 198 条幽灵行是"感觉重复源特别多"的一大来源。它们在库里、在统计里、在回收站视图里，但文件早就不在那个路径下了。

### 3.4 压缩包条目模型实际未启用

`entry_index > 0` 的记录数 = **0**。

影匣代码支持"一个 ZIP 装多集、每集独立进度"（`media.rs` 的 `entry_index` 语义），但实际使用中全是散文件。这条设计在库里零数据。

**这反而大幅简化了去重**：不用考虑"同压缩包不同集"的边界，按文件内容哈希就够。

### 3.5 接触表覆盖率 36%

698 / 1946 有接触表。其余打开时现场抽帧。这是 2.2 卡顿的直接来源。

## 4. 三项功能的实现评估

### 4.1 网格缩放 — 简单（半天）

**现状**：`App.css:200` 硬编码 `grid-template-columns: repeat(auto-fill, minmax(208px, 1fr))`。无任何缩放能力。

**方案**：
- CSS 改为 `minmax(var(--card-min, 208px), 1fr)`，卡片尺寸由 CSS 变量驱动。
- `Settings` 加 `grid_zoom?: number`（0.6 ~ 1.8，默认 1.0）。`Settings` 结构已有 `show_card_info?: boolean` 等可选字段先例，加字段无障碍。
- 工具栏加滑杆或 `-`/`+` 按钮；`Ctrl + 滚轮` 也可绑（需注意别与现有 wheel 处理器抢事件——画匣在这上面踩过坑）。
- 存 localStorage 即时生效 + 写回 settings 持久化。

**风险**：低。唯一要注意的是窗口化渲染的行高计算依赖卡片尺寸，改完需同步更新虚拟列表的估算高度，否则滚动位置会跳。

### 4.2 内容去重 — 中等（1~2 天）

**现状**：`db.rs:154` 的 `normalize_and_dedupe_videos` 只做**路径规范化**去重（统一 `/` 与 `\`、合并同路径多登记），**不看内容**。`blake3` 已在依赖里（`Cargo.toml:33`，目前只用于封面缓存 key）。

**方案**：
- 加 `fingerprint` 列（`ALTER TABLE videos ADD COLUMN fingerprint TEXT`）。
- 指纹算法：`blake3(首 8MB + 文件大小 + 尾 8MB)`。比全量哈希快一个量级——10.9GB 的文件从分钟级降到亚秒级，且对视频文件几乎不会误判（同大小 + 首尾 16MB 一致的概率极低）。
- 后台任务分批算指纹（每批 50 个，避免卡 UI），带进度事件。
- 命中重复后策略：**保留 `watch_count` 高的 / `last_watched_at` 新的那份**，其余标记 `trashed=1` 并记 `dedup_of=<保留 id>`；不直接删文件，让用户在回收站里确认后再删。
- 首轮清理预期回收 **23.2GB**。
- 同时清掉 3.2 和 3.3 的幽灵行：`trashed=1` 且文件不存在的，直接删记录。

**风险**：中。
- 误判风险极低但非零（首尾相同中间不同的剪辑变体，比如同片头同片尾不同正片）。建议首轮只做"完全同大小 + 首尾哈希一致"，并在 UI 里列出待清理项让用户过一眼，不做全自动。
- 跨盘复制时 mtime 会变，所以**不能用 mtime 参与指纹**。

### 4.3 hanime 插件 — 最重（4~6 天）

**现状：影匣里零 hanime 代码**（全仓 grep 无匹配）。现有 `downloader.rs` 是通用网页直链抽取器：

- `extract_candidates` 用正则抓 `.mp4/.webm/.m3u8/.zip/.jpg` 等后缀的 `href|src|content|url`。
- `download_one` 调系统 curl，支持 `-C -` 断点续传。
- 无站点专属解析、**无 cookie 注入**、**无 HLS 分片下载**、无元数据采集。

**hanime1.me 的实际差距**：

| 能力 | 现状 | 需要 |
|---|---|---|
| 页面解析 | 通用正则 | 站点专属：从页面内嵌 JSON / `data-*` 取标题、作者、tag、封面、原链接 |
| 登录态 | 无 | curl `-b` 或 `-H "Cookie: ..."` 注入；凭据存 Windows 凭据管理器，**不进代码/库/日志** |
| 视频流 | 只认直链 | 大概率是 HLS（`.m3u8`）→ 需 ffmpeg 拉流，或自解析 m3u8 分片下载后拼接 |
| 画质选择 | 无 | 会员画质需登录；按 m3u8 的 `RESOLUTION` 选最高 |
| 元数据入库 | `videos` 表无这些列 | 新增 `source_site` / `source_url` / `author` / `source_tags` 列 + 详情页展示 |
| 入库路径 | 下载落到 `<root>\downloads` | 落到区间夹，走统一 `pick_target` 分配 |

**关键设计建议**：抽一层 `SiteResolver` trait。

```
trait SiteResolver {
    fn matches(&self, url: &str) -> bool;
    fn resolve(&self, url: &str, cookie: Option<&str>) -> Result<ResolveReport>;
}
```

`hanime1.me` 实现这个 trait，通用正则解析器作为 fallback。这样以后加别的站点就是加一个 impl，不用动 `downloader.rs` 的 329 行主干。

**风险**：高。
- **站点改版即失效**，解析逻辑需可热更新或至少易改。
- **防盗链**：m3u8 分片常带 `Referer` 校验，curl/ffmpeg 都要带对。
- **凭据安全**：cookie 绝不能进代码、入库存明文、写日志、进广播。走 Windows 凭据管理器（`wincred`）或 DPAPI 加密的本地配置。
- **法律与账号风险**：自动抓取可能触发站点风控。建议限速、单任务串行、失败退避。

## 6. 关于"臃肿"的判断

**臃肿是真实的，但不是垃圾代码堆积。** 13976 行支撑了视频扫描、mpv 播放、接触表、区间夹、批量编辑、下载、老板键、沉浸模式、合集画廊、快捷键可配这一整套功能，代码密度合理，后端错误处理干净。

真正的问题是**结构**不是**体量**：三个巨型文件吃掉了 45% 代码，全部职责挤在少数几个入口里。这导致：

- 改一处要读 1900 行上下文（`App.tsx`）
- 28 个 `useEffect` 的依赖数组互相牵制，白屏 bug（React #310）就是这么来的——0.1.26 修的就是"hook 在早退之后"的位置问题
- 新功能（hanime、网格缩放）没有干净的插入点，只能继续往巨头文件里塞

**结论**：先做 P0/P1（数据清理 + 去重 + 缩放 + 接触表），这些不碰结构、风险可控、收益立即可见；P2 的拆分放在功能稳定后单独排一个批次，因为拆 `App.tsx` 必然带来一轮回归测试，不适合与其他改动混在一起。
