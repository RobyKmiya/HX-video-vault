# 影匣接入画匣（双匣合并）· 调研与导入方案

> 调研日期：2026-11-26　调研人：workbuddy　性质：**只读调研 + 方案设计，未改任何代码**
> 触发约定：**画匣发 1.2.0 时再正式启动合并**。在此之前所有条目都是"预备"，不施工。
> 调研对象：画匣 `D:\Qoderwork`（HEAD `b51a0bf`，版本 1.1.58）；影匣 `E:\VideoVault`（HEAD `b3321e1`，版本 0.1.26）。
> 调研方式：通读两侧 `package.json` / `Cargo.toml` / `tauri.conf.json` / 前端 hooks / Rust 模块 / `db.rs`，并以只读方式核对真实库（画匣 `F:\Hthings\BENZI\.gallery\library.db` user_version=13；影匣 `F:\Hthings\Supervideo\.vault\vault.db` user_version=6）。

---

## 一、结论先行

合并**技术上可行，但不是"把两个仓拷到一起"那么简单**。真正的拦路虎只有三个，其余都能靠架构分层化解：

1. **数据模型粒度根本不同**——画匣是"一本 = 一个文件"，影匣是"一条 = (文件路径, 压缩包内条目序号)"。这是语义层差异，不能靠改表名绕过。
2. **两套独立数据库 + 两套迁移框架**——`library.db` v13 与 `vault.db` v6，表名撞车但字段语义不同。
3. **影匣的 mpv 是独立顶层窗口**——画匣是纯 WebView，藏窗/沉浸/标签页这套壳对独立窗口管不住。

结论方向：**以画匣的工作台标签壳为容器，影匣作为"视频领域包"接入，双库并存、共享层复用、合库作为最后可选项甚至永不做**。这样风险可控、可回退，且不用推翻任何一侧已经稳定的功能。

---

## 二、共同之处（合并的地基）

两侧是同源团队用同一套脚手架写出来的，重合度比想象中高得多。

| 维度 | 画匣 | 影匣 | 合并含义 |
|---|---|---|---|
| 前端栈 | React 19 + Vite 8 + TS 6 | 完全相同 | 组件可直接互相搬，无需转译 |
| 桌面壳 | Tauri 2 | Tauri 2 | 同一套插件体系 |
| 数据库 | rusqlite 0.43 bundled | 完全相同 | 驱动层零成本统一 |
| 状态管理 | 无 router、自研状态机 + hooks | 完全相同（画匣=TabKind，影匣=ViewKey） | 需要一层统一外壳把两套状态机包起来 |
| UI 基建 | Toast / ReaderMenu / Splitter / layout.ts / gestures.ts / shortcuts.ts | 一一对应、几乎同名同构 | **共享层的现成素材**，选一侧留下即可 |
| 窗口能力 | 自绘无框、沉浸去标题栏、老板键、几何恢复 | 同款实现 | 可直接合并成一套 |
| 数据语义 | 收藏/待看/标签/评分/备注/进度/软删/回收站 | 同款语义（只是对象不同） | 概念层统一，字段层隔离 |
| 工程配套 | 单实例守卫、每日备份、WAL、CLI（galleryctl） | 单实例守卫、每日备份、WAL、CLI（vaultctl） | 模式一致，可共用骨架 |

一句话：**两边就像同一套乐高按两张图纸拼出来的两个模型**，零件通用，拼法不同。合并就是重新设计一张图纸，而不是重新造零件。

## 三、困难所在（真正的硬骨头）

### 1. 数据模型粒度不同（最关键）
- 画匣 `archives.rel_path UNIQUE`：一本漫画 = 一个文件，进度是"第几页"。
- 影匣 `videos` 主键是 `(path, entry_index)`：一个 ZIP 里可能有十几集，每集有自己的时长、进度、观看次数。
- 影匣代码注释里明确写过"画匣是『一本 = 一个文件』，视频不能照搬"。
- **不能做的事**：把 videos 塞进 archives 表、或让 collections 同时挂画集和视频条目而不区分类型。强行统一会让两边的进度语义互相污染。

### 2. 两套数据库与迁移框架
- 画匣 `<库根>\.gallery\library.db`，v13，20+ 张表，含 FTS5 全文索引和大量触发器。
- 影匣 `<库根>\.vault\vault.db`，v6，7 张表，v6 迁移里还有一次"路径规范化 + 去重 + 清库外残留"的数据清洗。
- 表名撞车但语义不同：`collections`、`tags` 两边都有，字段和约束不一样。
- 两侧迁移都是"建表 IF NOT EXISTS + 按版本补列"的累计式实现，各自内嵌在自家 `db.rs`（画匣 3290 行、影匣 2673 行）。
- **不能做的事**：让一个 `user_version` 同时管两套 schema。

### 3. mpv 独立顶层窗口
- 影匣用 `--force-window=yes` 起 mpv 作为**独立顶层窗口**，靠命名管道 `\\.\pipe\video-vault-<pid>` 做 JSON IPC。
- 画匣整个界面都在一个 WebView 里，沉浸、标签、模态都靠 CSS/DOM。
- 后果：合并壳里的"标签页切换""老板键藏窗""沉浸无边框"都管不到 mpv 窗口。影匣现在的规避办法是藏窗前先停 mpv，但合并后标签页切走也面临同样问题。
- 另外 mpv/VLC/ffmpeg/ffprobe/curl 这些外部进程，画匣一侧完全没有，是一整套新的资源调度。

### 4. 全局资源冲突
- 老板键 `Ctrl+Shift+H` 是系统级全局热键，两侧都注册，合并会抢注。
- 单实例互斥体两边名字不同（`VideoVault.SingleInstance.v1` / `com.archivegallery.desktop.single-instance`），但合并后必须只留一套。
- asset 协议 scope：影匣放开 `$HOME` + `E:/D:/F:` 盘，画匣只放 `$APPCACHE` + 自定义 `gallery:` 协议。合并要取并集，但放宽 scope 会扩大安全面。
- 配置目录、localStorage 键空间（`vv.*` vs `huaxia.*`）、dev 端口（1421 vs 1420）全都不同，需要命名空间隔离。

### 5. 视图外壳没有统一层
- 画匣：`TabKind` 标签状态机（`WorkspaceTabs.tsx`，含多 webview 挂载与模态让位总线）。
- 影匣：`ViewKey` + 导航历史栈（`App.tsx` 里约 40 个 useState）。
- 两边主组件都很大（画匣 `LibraryView.tsx` 4178 行、`Reader.tsx` 2470 行；影匣 `App.tsx` 1893 行）。没有 router 意味着合并要先造一个能同时容纳两套状态机的壳。

### 6. 扫描模型不同
- 画匣扫图集压缩包，按页缓存（`pagecache.rs` 256MB LRU）。
- 影匣全库递归扫描 + ffprobe 并行探测 + 接触表抽帧 + 区间夹导入（每夹 200 条）。
- 两套后台任务并发时的 IO/CPU 争用需要统一调度。

## 四、兼容方向（四条原则）

1. **共享层抽公共，领域层各自留**——不追求"一份代码两边用"，追求"一份实现双方调用"。
2. **双库并存优先于合库**——两个 db 文件用命名空间隔离，各管各的 schema 和迁移。合库不是目标，是可选终点。
3. **以画匣工作台为壳**——画匣的 `TabKind` 天然能扩展出一个"视频"标签，影匣作为领域包挂进去，比反过来把漫画塞进视频侧栏自然得多。
4. **全局资源单点管理**——单实例、热键、配置、asset scope、外部进程队列，合并后必须收敛到一个入口，按窗口 label / 领域分派。

---

## 五、设计思路（三层架构）

```
┌─────────────────────────────────────────────┐
│ L2 外壳层（新建）                            │
│  统一 TabKind（home/gallery/video/browser…） │
│  统一侧栏 / 统一设置 / 统一启动屏 / 统一搜索   │
├──────────────────────┬──────────────────────┤
│ L1 领域包 A：漫画      │ L1 领域包 B：视频      │
│  db(gallery) v13      │  db(vault) v6         │
│  archive/reader/      │  mpv/media/scan/      │
│  importer/loose/      │  importer/edit/       │
│  netdl/d2/tags        │  downloader/player    │
├──────────────────────┴──────────────────────┤
│ L0 共享内核（从两侧抽取，取一为主）            │
│  窗口/沉浸/老板键/单实例 · Toast/ContextMenu/  │
│  Splitter/layout/shortcuts/gestures · proc::quiet│
│  配置读写/每日备份/asset 协议 · 命令前缀规范    │
└─────────────────────────────────────────────┘
```

**L0 共享内核**：两侧现成的同构组件就是素材库。选画匣版或影匣版为主（建议选功能更全的一侧），另一侧改为调用。关键动作是**命令加领域前缀**（`gallery_*` / `video_*`），localStorage 键统一加命名空间，避免串值。

**L1 领域包**：两套 db + 各自领域模块原样保留，只把对外接口改成"注册到外壳"。视频包把 mpv 窗口生命周期纳入外壳管理（切标签=停会话，藏窗=停会话）。

**L2 外壳层**：TabKind 扩出 `video`；侧栏按当前标签切换领域导航；设置页合并成"通用 + 漫画 + 视频"三段；启动屏用影匣那套更完整的（画匣目前只有一个转圈 div，影匣有分阶段进度文案和保险丝）。

## 六、分阶段导入方案（以 1.2.0 为触发点）

### 阶段 0 · 预备（1.2.0 之前，本次不做）
目标：让两侧同构组件行为一致，降低将来合并的 diff。
- 把两侧 Toast / ContextMenu / Splitter / layout / shortcuts / gestures 的接口对齐，选一侧为实现蓝本。
- 命令命名提前加领域前缀，localStorage 键提前加命名空间。
- 这些改动在各自仓里独立发版，**不算合并**，风险为零。

### 阶段 1 · 合壳（1.2.0 落地，最小可行合并）
目标：一个 exe、一个窗口、两个领域标签，双库并存。
- L0 共享内核抽出，画匣工作台壳扩出 `video` TabKind。
- 影匣以领域包接入，仍用 `vault.db`，不改 schema。
- mpv 生命周期接入标签切换与藏窗：切走/藏窗先停会话。
- 全局资源收敛：一套单实例、一套热键（按当前标签分派）、asset scope 取并集。
- 验收标准：两个库都能读、都能播放/阅读、切标签不串、老板键只藏当前应用、数据零丢失。

### 阶段 2 · 体验统一
- 统一侧栏/设置/启动屏/回收站入口。
- 外部进程统一调度：扫描、抽帧、下载共用一个任务队列和工具路径配置。
- 跨领域搜索（可选）：一个搜索框分别查 archives 和 videos。

### 阶段 3 · 数据互通（可选）
- 统一"库注册"概念：一个应用可挂多个库，每个库标 `kind=gallery|video`。
- 跨媒体收藏/标签的关联视图。

### 阶段 4 · 合库（可选，风险最高，也可永久不做）
- 只有在前三个阶段稳定运行很久、且确有必要统一查询时才做。
- 必须带双向迁移工具和回滚闸门，迁移前强制备份。
- 建议默认不做——双库并存的维护成本远低于合库的风险。

## 七、潜在风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 数据迁移不可逆、用户标签/观看历史丢失 | 高 | 阶段 1–3 一律双库不动 schema；合库只在阶段 4，强制备份 + 回滚闸门 |
| mpv 独立窗口在合并壳下藏窗/切标签残留 | 高 | 生命周期纳入外壳：切标签/藏窗/退出前先 stop 会话；保留"播放器已接管"占位层 |
| 全局热键抢注、藏窗逻辑互相覆盖 | 高 | 一套全局注册表，按当前标签/窗口 label 分派；注册失败回滚 UI |
| localStorage 键撞车导致配置串值 | 中 | 迁移前统一加命名空间（`hx.*` / `vv.*`），读时再校验 |
| asset scope 放宽扩大安全面 | 中 | 按领域动态授权，不一次性全放；视频盘符 scope 只在视频标签激活时给 |
| 两套 release / identifier / 安装位并存导致升级混乱 | 中 | 合并前定死一个 identifier 和一个安装位，旧版做卸载引导 |
| 大组件合并引入回归 | 中 | 领域包黑盒接入，外壳只调接口；每阶段保留完整回归测试（两侧现有 55+/69+ 测） |
| 1.2.0 是否真会来、何时来不确定 | 中 | 见下节——这是当前最需要先确认的前提 |

## 八、1.2.0 触发前必须先确认的事

调研里有个重要发现：**画匣仓库内目前没有 1.2.0 路线图**。全仓只有 `docs/logs/2026-11-18-one-command-release.md` 里一处 `node scripts/release.mjs --set 1.2.0` 的脚本示例，没有任何合并相关的设计条目。当前 HEAD `b51a0bf` 的实际版本是 **1.1.58**（相比已广播的 `51721f3` 只多了"内置画匣盾脚本 + 版本号抬升"两个提交）。

所以在动手之前，需要先回答三个问题，否则"1.2.0 时再合并"会落空：

1. 1.2.0 到底包含什么？合并是 1.2.0 的主题，还是 1.2.0 之后才启动？
2. 合并后应用叫什么、identifier 用什么、旧的两个安装位怎么处置？
3. 两个库（画匣 BENZI、影匣 Supervideo）物理上要不要放同一个根？如果放，`.gallery` 和 `.vault` 同级并存是否接受？

补充一条协作状态提醒：本次调研发现画匣 `b51a0bf`（1.1.58）的增量尚未在广播站单独广播，属于其它施工批次的收尾缺口。我这次是纯调研、没有装机发版，因此**没有代它广播、也没有推广播水位**，避免把不是本次完成的工作虚报成我的交付。需要的话由对应施工方补一条即可。
