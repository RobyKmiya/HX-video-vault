> 状态：方案立项 + 骨架已落地（v0.1.0）。所有后续施工以 `D:\Qoderwork\docs\施工日志.md` 为准。

## 一、一句话定位

**给个体用户的、零服务器的、压缩包一等的本地视频库**——用画匣的管理手感管视频，但不把漫画那套照搬过来。

关键判断：视频和漫画的管理单位不同。漫画是「一本 = 一个文件/目录」；视频是「一个容器可能装几十集」，而且**观看进度是按秒算的**。所以影匣的数据库主键是 `(path, entry_index)` 而不是文件路径，每一集都能单独记进度、打标签、算观看次数。

## 二、现成方案调研：他们强在哪，为什么还不够

### 2.1 播放器侧

| 产品 | 值得学的点 | 为什么不能直接当「影匣」 |
| --- | --- | --- |
| **VLC** | 格式兼容天花板、插件/demux 架构、`libvlc` 可嵌入、跨平台 | 它是播放器不是库：没有标签体系、没有备注/评分、搜索只能按文件名；界面为「打开一个文件」设计，不是为「在 2000 条里找一条」设计 |
| **mpv** | 极简内核 + IPC/脚本可编程、`--wid` 可嵌窗口、进度/截图脚本化 | 同样不管库；配置靠文本文件，普通用户门槛高；无中文标签/分类树概念 |
| **PotPlayer / MPC-HC(BE)** | 面板布局成熟、快捷键密集、播放列表体验好 | Windows 专属、闭源或停更多年，无法内嵌进 Tauri 做数据联动 |
| **IINA** | 原生 macOS 体验、交互克制、预览条做得漂亮 | 平台不符；无库管理 |
| **SMPlayer** | 记忆播放位置、YouTube 集成 | 记忆是单文件的临时状态，不是可统计的历史数据 |

### 2.2 个人媒体库侧

| 产品 | 强项 | 个体本地场景的痛点 |
| --- | --- | --- |
| **Jellyfin / Plex / Emby** | 元数据抓取、海报墙、多端串流、观看进度同步 | 要常驻服务器；元数据联网抓取（成人内容、私密视频不友好）；**压缩包基本不管**；装一套只为管本机文件太重 |
| **Kodi** | 本地库 + 插件生态 | 界面偏电视遥控器逻辑，整理上千文件的手工成本很高；配置复杂 |
| **Filebot** | 批量重命名/整理，匹配影视数据库 | 是「整理工具」不是「日常浏览工具」；无播放、无备注、无观看统计 |
| **TinyMediaManager / MediaElch** | 刮削、NFO、剧集管理 | 面向影视收藏家，流程重；不适合混合类型的个人视频（录屏、直播录像、短片、图包视频） |

**结论**：播放器不懂库，库管理器不懂本地压缩包和隐私。中间这块是空的。

## 三、影匣的差异化（8 条）

1. **压缩包一等公民**：ZIP/CBZ 内视频通过 Central Directory 逐条登记，播放时只解出那一个文件到缓存，不整包解压。Plex/Jellyfin 对压缩包基本无解，VLC 只能当普通文件打开。
2. **条目级进度与次数**：`(path, entry_index)` 粒度，第 3 集看到 12:34 和第 5 集没看过是两条独立状态。播放器只记「上次位置」，媒体服务器只记整集。
3. **接触表（contact sheet）而不是单封面**：ffmpeg 每 45 秒抽一帧拼 4×4 图，一张图看完整个视频的内容走向。对录屏/直播录像/无元数据视频尤其有效——这正是影视刮削器不适用的场景。
4. **零服务器、零联网**：所有数据在本机 SQLite；不擅自把文件名、路径、封面发给任何服务。画匣的隐私铁律同样适用于影匣。
5. **画匣式管理手感**：未分类标签置顶、分类可折叠、标签权重、收藏夹、待看清单、批量打标、统一回收站、组合筛选——这些是漫画库打磨出来的高频操作，视频库同样需要，但现成播放器都没有。
6. **统计是给「我」看的**：库容量、总时长、观看覆盖率、最近入库、标签分布。不搞社交、不搞推荐算法。
7. **可脚本化**：预留 `vaultctl` CLI（与画匣的 `galleryctl` 同思路），供自动化与 agent 调用，不把能力锁在 GUI 里。
8. **渐进式播放内核**：常见格式用内置播放器（自研控件），冷门格式外挂本机 VLC 从上次位置续播，后续可换 libmpv IPC 内嵌——不押注单一解码实现。

## 四、上千视频如何统计 / 标记 / 管理

### 4.1 数据模型（schema v1 已落地）

- `videos`：`path + entry_index` 唯一；元数据（大小、mtime、时长、分辨率、音视频编码）、观看数据（次数、秒级进度、上次观看、完成）、评分、备注、收藏、回收站、接触表路径、`tag_text` 冗余列。
- `tags` / `video_tags`：名称、大类、权重；标签挂载后自动重算 `tag_text` 供搜索。
- `collections` / `collection_videos`：系统目录（待看）+ 自建目录。
- `watch_history`：每次观看的起止秒与是否看完。
- `download_tasks`：预留给后续网页下载器（状态、进度、目标路径、错误）。
- 每日 `VACUUM INTO` 快照，滚动保留 3 份。

### 4.2 统计口径

| 指标 | 口径 |
| --- | --- |
| 视频条目 | 压缩包内每集各算一条 |
| 文件/压缩包 | `COUNT(DISTINCT path)` |
| 占用空间 | 按条目累加**容器文件大小**（同一包内多集不重复计入 `archive_count`，但 `total_bytes` 需要去重——列为待修项） |
| 观看次数 | 进度回退到 50% 以下或 ≤1 秒才计新会话，避免拖动进度条刷次数 |
| 看完 | 进度 ≥ 95% 或手动标记 |
| 观看覆盖率 | `watch_count > 0` 的条目 / 总条目 |

### 4.3 标记习惯（建议）

- **状态类标签**：`已整理` / `待复查` / `精华`，配权重控制待看优先级。
- **内容类标签按大类分组**：如 `作者`、`系列`、`题材`、`来源`，标签中心里大类折叠。
- **备注**记剧情线索/时间点（"02:15 那段"），搜索框会一起搜。
- **待看清单**用目录而非标签，避免和分类标签混用。
- **批量操作**：Ctrl/Shift 多选 → 批量打标 / 加入待看。

### 4.4 千级流畅度

- 递归扫描只读 Central Directory，ffprobe 只对视频文件跑；扫描放阻塞线程池，不卡 UI。
- 列表分页 48 条 + 加载更多；接触表懒加载。
- 抽帧是昂贵操作，独立于扫描，按需触发，结果缓存进 `.vault/cache/contacts`。
- 压缩包条目按需解压，缓存按 `blake3(path|index)` 命名，重复访问不重复解压。

## 五、播放器架构与 VLC 调研

### 5.1 本机 VLC 实测

- 安装位置：`C:\Program Files (x86)\VideoLAN\VLC\vlc.exe`、`D:\TOOLS\VLC\vlc.exe`，版本 **3.0.21**。
- **本机没有 VLC 源代码，也没有 SDK 头文件**（`libvlc_media_player.h` 等不存在）；安装包只含二进制与插件。
- 官方源码/文档：VideoLAN GitLab `https://code.videolan.org/videolan/vlc`；libvlc 文档 `https://www.videolan.org/developers/libvlc.html`。

### 5.2 决策

- **不移植 VLC 解码逻辑**，把它当黑盒：外挂播放用 `--start-time=<秒>` 续播。
- 内置播放器用前端 `<video>` + 自研控件（播放/倍速/音量/截图/全屏/续播/上下集），覆盖 mp4/webm/mov 等。
- 后续若要嵌入统一窗口，优先评估 **libmpv + IPC**（ISC 许可、可编程、`--wid` 嵌窗），libvlc 作为备选（LGPL，需随包分发 DLL，体积大）。
- VLC 源码里值得学的：模块/插件架构、demux 与 decoder 分离、input item 与 meta 抽象、playlist 抽象。**这些是解码器的组织方式，不是媒体库的数据模型——不要照搬。**
