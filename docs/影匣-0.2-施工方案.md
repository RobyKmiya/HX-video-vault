## 0. 结论先行

| # | 问题 | 根因（一句话） | 方案 | 工作量 |
|---|---|---|---|---|
| R1 | 文件夹永远占着主区 | 主区无条件渲染 `folder-strip` 网格（`App.tsx:772`），而库里有 40 个 auto 夹 | 降级为「侧栏折叠树 + 独立文件夹页」，主区只在进夹时留面包屑 | 中 |

| R5 | 库内不能改名/移动文件 | 只有软删，想改名只能开资源管理器，改完还得重扫 | 应用内**重命名 / 移动 / 资源管理器定位**；同盘走 `fs::rename`（元数据操作），封面按 id 缓存不重抽 | 小（**已落地 0.1.24**） |

## 三、设计理念与风格

影匣当前有**三套**互不相干的视觉语言，这是"不像一个产品"的根源：

1. 库区：浅色（`--bg #f6f7f9`，`App.css:1-23`）
2. 启动屏：深色胶片扫光（`App.css:41-48`）
3. 播放页：深色遮罩（`player-overlay`）

### 3.1 定位一句话

> 画匣是**纸**（浅、密、像书架）；影匣是**胶片**（暗、亮、像放映厅）。
> 库区可以浅，但播放必须是影厅。

统一规则：**库区跟随主题（浅/深/自动），播放页与启动屏恒为暗色**，两者交界用 320ms 的 `--ease-curtain` 过渡，不做闪白。

### 3.2 设计令牌（新增 `src/tokens.css`，被 App.css `@import`）

```css
:root{
  --dur-fast:120ms; --dur-base:220ms; --dur-slow:320ms;
  --ease-out:cubic-bezier(.2,.8,.2,1); --ease-curtain:cubic-bezier(.4,0,.2,1);
  --z-drawer:30; --z-menu:9000; --z-toast:9500; --z-veil:9999;
  --card-s:168px; --card-m:216px; --card-l:280px;   /* 三档密度 */
}
[data-theme="dark"]{ --bg:#0e1118; --surface:#161b24; --surface-2:#1c222d; --surface-3:#242b38;
  --text:#e6e9f0; --muted:#8a93a5; --line:#252c38; --line-strong:#333c4c; }
```

### 3.3 三档密度与「画面收缩」

断点不看屏幕宽度，看**主区可用宽度**（窗口宽 − 侧栏），用 `ResizeObserver` 落到 `<html data-density>`：

| 主区宽 | 密度 | 卡片 | 侧栏 | 详情 |
|---|---|---|---|---|
| ≥ 1100 | `L` | 280px | 完整 | 抽屉 420px 常驻 |
| 720–1099 | `M` | 216px | 完整 | 抽屉浮层 |
| 460–719 | `S` | 168px | 紧凑（无文字） | 全屏抽屉 |
| < 460 | `XS` | 168px | 图标态 62px | 全屏抽屉 |

与画匣同一教训：**宽度钳制只能在 `usePersistentSize` 那一处，Splitter 的 min 必须与其相等**（1.0.76 踩过两层不同步）。

### 3.4 动效克制

现有 `.video-card:hover img{transform:scale(1.04)}`（`App.css:196`）在几十张卡同时 hover 时掉帧，改为只改 `border-color + box-shadow`，`transform` 只保留 `translateY(-2px)`。

## 四、四项硬需求施工方案

### R1 文件夹不再常显

**现状**：`App.tsx:772-800` 无条件渲染 `<section className="folder-strip">`，网格 `auto-fill minmax(168px,1fr)`（`App.css:551`）。顶层 6 个夹时占一行，进 `BENZI`/`Supervideo` 这种多子目录的夹会堆 2–3 行，把影片墙推到首屏之外。

**改造（三层分离）**

1. **侧栏「文件夹」折叠树**（新组件 `components/FolderTree.tsx`）
   - 位置：`资料库` 与 `标签` 之间，标题行右侧一个折叠箭头
   - 默认**收起**，只显示一行 `文件夹 · 40`
   - 展开后按**源分组**（见 R2），每级可再展开；状态存 `localStorage["vv.folders.expanded"]`
   - 只在 `folderPath` 为空时列出顶层；进入某层后该层高亮
2. **主区不渲染文件夹网格**
   - 删除 `App.tsx:772-800` 整段
   - 只在 `folderPath.length > 0` 时保留面包屑（`App.tsx:752-770`，已有）
   - 面包屑右侧加「↑ 上一层」与「在本层搜索」
3. **独立「文件夹」视图**（侧栏 nav 一项，`ViewKey` 加 `"folders"`）
   - 整页展示文件夹墙：按源分区、支持名称/数量/最近修改排序、三档密度、双击进夹
   - 这是"单独排列方式"的落点：需要看全局结构时进来，日常不进
4. **附注**：`おきたつきOkitatsuki` 有 36 条但无 auto 夹 —— 说明 `sync_folder_collections` 的 `dir_ids` 只收"本次 seen 的路径"（`db.rs:1110-1122`），若该目录上次扫描后新增文件、而该目录本身没被重新镜像是会漏的。R2 改造时一并修：**auto 夹的创建依据改为"磁盘上存在的目录"，而非"本次出现的文件所在目录"**。

**验收**：进「全部视频」，首屏第一行必须在影片墙而非文件夹卡；侧栏「文件夹」默认收起；`localStorage` 记住展开状态。

### R2 多源：只选视频目录

**现状**：`settings.library_root = "F:\Hthings"`，`scan` 对整个根做 `WalkDir(max_depth 12)`（`lib.rs:297-313`），`sync_folder_collections` 把**每个含视频的子目录**镜像成 `kind='auto'` 收藏夹（`db.rs:1126-1141`）。结果：画匣的 `BENZI`、图片库 `PIXIVS&Ehentai`、`散图`、`种子库` 全被纳入。

**语义重构（关键）**：把「库」和「源」拆开。

- **库**（`library_root`）：`.vault`（数据库 + 缓存）所在，可以很小，只放元数据
- **源**（`sources`）：真正的媒体目录，可多个、可跨盘、可随时增删，**不复制文件**

#### schema v6

```sql
CREATE TABLE IF NOT EXISTS sources (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  path          TEXT    NOT NULL UNIQUE,
  label         TEXT    NOT NULL DEFAULT '',
  enabled       INTEGER NOT NULL DEFAULT 1,
  exclude_names TEXT    NOT NULL DEFAULT '',  -- 分号分隔，目录名精确匹配
  added_at      INTEGER NOT NULL DEFAULT 0,
  last_scan_at  INTEGER NOT NULL DEFAULT 0
);
ALTER TABLE videos      ADD COLUMN source_id INTEGER NOT NULL DEFAULT 0;
ALTER TABLE collections ADD COLUMN source_id INTEGER NOT NULL DEFAULT 0;

-- 顺带补齐 R4/性能需要的索引
CREATE INDEX IF NOT EXISTS idx_cv_video    ON collection_videos(video_id);
CREATE INDEX IF NOT EXISTS idx_videos_trash ON videos(trashed, added_at DESC);
CREATE INDEX IF NOT EXISTS idx_videos_fav  ON videos(favorite, trashed);
CREATE INDEX IF NOT EXISTS idx_videos_src  ON videos(source_id, added_at DESC);
CREATE INDEX IF NOT EXISTS idx_videos_name ON videos(file_name COLLATE NOCASE);
```

#### 迁移（v5 → v6，自动、幂等）

1. 若 `sources` 空：把 `settings.library_root` 插成第一条源，`label="原库目录"`，`enabled=1`
2. `UPDATE videos SET source_id = (SELECT id FROM sources ORDER BY id LIMIT 1) WHERE source_id=0`
3. `collections(kind='auto')` 的 `source_id` 按成员多数归属回填
4. 不改任何 auto 夹名字（避免用户视图跳变）；**显示时**加源标签区分

#### 扫描改造（`lib.rs:256-409`）

- 入参改为 `ScanOptions { source_ids: Option<Vec<i64>>, recursive, entry_limit }`；`None` = 全部启用的源
- 每个源独立 `WalkDir`，`filter_entry` 额外排除：`.vault`、`.gallery`、`$RECYCLE.BIN`、`System Volume Information`、以及该源 `exclude_names` 里的目录名
- `sync_folder_collections(conn, source, seen_paths)` 增加 `source_id` 维度；auto 夹名保持相对路径，`source_id` 记归属
- 进度事件加 `source` 字段，前端显示"正在扫描 ClassicalSUM（738 条）"

#### 存量清理：把 BENZI 踢出库（一次性、可回滚）

新命令 `detach_source(source_id, purge_records: bool)`：
1. 该源下所有 `videos` 置 `trashed=1`（**不动磁盘文件**）
2. 删除该源的 auto 夹与 `collection_videos` 关联
3. 写一条 `detach_log`（时间、条数、源路径），可从回收站恢复

**给用户的建议清单**（基于实测，建议写进设置页的"源管理"里）：

| 源目录 | 建议 | 依据 |
|---|---|---|
| `Supervideo` | 保留（主力） | 2136 条 |
| `ClassicalSUM` / `Cunny +` / `MOST` / `Hutao&Furina` / `B` / `萝莉` / `おきたつき…` | 保留 | 共 1528 条视频 |
| `BENZI` | **移除**（属画匣） | 6 条 zip，是画集包 |
| `PIXIVS&Ehentai` / `散图` / `种子库` | **不加入** | 图片/种子，非视频 |

**验收**：`videos` 里 `source_id` 无 0 值；设置页能增删启用源；扫描只走选中源；`BENZI` 条目为 0 且磁盘文件未被触碰。

### R3 库内文件管理

现有批量条（`App.tsx:802-852`）只有：批量打标、拼接、加入待看、加入收藏夹、取消选择。补齐到 7 个动作：

```
已选 12 条   [播放] [加入收藏夹 ▾] [加入合集 ▾] [批量打标] [导入到本层] [删除] [彻底删除]
```

#### 后端命令（`src-tauri/src/lib.rs`）

```rust
trash_videos(ids: Vec<i64>) -> usize;                       // 软删（已有单条 trash_video，扩成批量）
restore_videos(ids: Vec<i64>) -> usize;                     // 从回收站恢复
purge_videos(ids: Vec<i64>, mode: String) -> PurgeReport;    // mode: "quarantine" | "hard"
reveal_in_explorer(path: String) -> ();                      // explorer /select,
import_into(parent: String, paths: Vec<String>) -> usize;    // 导入到指定文件夹
```

#### `purge_videos` 的三档语义（安全优先）

| 档 | 行为 | 可撤销 | 触发 |
|---|---|---|---|
| 软删（默认） | `trashed=1`，文件不动 | 是 | 批量条「删除」 |
| **移入隔离区**（推荐默认"彻底删除"） | `fs::rename` 到 `<lib>/.vault/quarantine/{id}__{name}` + 写 `quarantine` 表；同盘秒移，**18GB 文件也不复制** | 是（30 天内） | 「彻底删除」第一击 |
| 硬删 | `remove_file` | **否** | 「彻底删除」第三击，需输入 `删除` 二字确认 |

- 压缩包内条目（`entry_index>0`）：只删记录，提示"该集在 `xxx.zip` 内，未动压缩包"
- 一次最多 50 条，逐条报错不中断，返回 `{done, failed: [(id, reason)]}`，前端弹清单
- **红线**：任何删除动作前端必须先弹可滚动的文件清单（完整路径 + 大小），用户确认后才发命令

#### 合集（照画匣 v11 移植）

```sql
CREATE TABLE IF NOT EXISTS series (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  note TEXT NOT NULL DEFAULT '',
  cover_video_id INTEGER REFERENCES videos(id) ON DELETE SET NULL,
  source_id INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL DEFAULT 0,
  deleted_at INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE IF NOT EXISTS series_items (
  series_id INTEGER NOT NULL REFERENCES series(id) ON DELETE CASCADE,
  video_id  INTEGER NOT NULL REFERENCES videos(id) ON DELETE CASCADE,
  position  INTEGER NOT NULL DEFAULT 0,
  label     TEXT NOT NULL DEFAULT '',
  PRIMARY KEY (series_id, video_id)
);
CREATE INDEX IF NOT EXISTS idx_series_items_video ON series_items(video_id);
```

- 约束与画匣一致：**一条视频只能在一个合集**；加入时若已在别的合集，弹「移出并加入 / 取消」
- 网格呈现：成员卡让位给一张「合集卡」（2.6s 轮换封面，照画匣 `SeriesCard` 交叉淡入）
- `SeriesDrawer`：改名、拖拽调序、改集数标签、设封面、移出、拆散（软删，成员回网格）
- 连播：`Player` 的 `onNext` 增加 `seriesCtx: {seriesId, position}`，末集后提示"下一合集"或退出
- 与收藏夹的区别写进 UI 说明：**收藏夹 = 多对多、无序；合集 = 一对多、有序、有集数**

**验收**：多选 5 条 → 加入合集 → 网格出现合集卡 → 点开按集数排 → 连续播放跨集不中断；彻底删除走隔离区后能在回收站恢复。

#### 为什么「快」

1. 同盘改名/移动 = `fs::rename`，纯元数据操作（毫秒级），不复制一个字节；18GB 文件也是瞬间。
2. 封面/接触表缓存按**视频 id** 命名（`cover-{id}.jpg`、`mid-{id}.jpg`、`sheet-{id}`），改名换夹后照样命中，**不重抽**。
3. 不做全库扫描：只处理这一条 + 它涉及的两个目录夹，1 次 UPDATE + 2~3 次小查询。
4. 重命名返回整条 `VideoItem`，前端就地替换；批量移动整体刷新一次列表。

#### 边界（安全优先）

- 只能移动到**库目录内**（`canonicalize` 后校验前缀），库外请用资源管理器。
- 压缩包内条目（`entry_index>0`）不能单独改名/移动/定位 —— 它们共用压缩包，UI 置灰并给提示。
- 目标同名不覆盖：自动 ` (2)`、` (3)`，跟资源管理器一致。
- 文件名校验：拒绝 `\ / : * ? " < > |`、结尾点/空格、Windows 保留名（CON/PRN/LPT1…）。

### R4 播放卡顿：五层诊断与优化

不是单一原因，是 5 层叠加。按"收益/风险"排序施工。

#### L1 全局锁串行化（收益高、风险低）

**证据**：`AppState` 是 `Mutex`，几乎所有命令第一行就是 `state.lock()?`。而 `playback_info` 是**同步命令**，在持锁状态下做三件事（`lib.rs:536-547`）：

```rust
let ctx = state.lock()?;                    // ← 全局锁
let info = player::resolve(lib, id)?;       // ← 压缩包条目会在这里解压
player::backfill_meta(lib, id, ...);        // ← 会 spawn ffprobe 进程
```

同一时刻 `query_videos`（`lib.rs:411-415`）、`video_cover`（`lib.rs:1020-1026`）、`mpv_open`（`lib.rs:813`）都在抢这把锁。**任何一次 ffprobe/解压期间，整个应用的 IPC 全部排队** —— 表现为"点一下没反应，然后一起反应"。

**改造**

1. `AppState` 拆锁：`db: Arc<Mutex<Connection>>`（短持有）、`settings: RwLock<Settings>`、`mpv: Mutex<Option<Arc<MpvSession>>>`、`cover_gate`
2. `playback_info` 改 `async` + `spawn_blocking`，且流程改成：短锁取 path → **锁外**解压/探测 → 短锁回填
3. `query_videos` 改 `async` + `spawn_blocking`（SQLite 查询不进 IPC 线程）

预期：交互延迟从"秒级卡顿"降到"无感"。

#### L2 封面在渲染路径里跑 ffmpeg（收益高、风险低）

**证据**：`useCoverSrc`（`cover.ts:55-87`）在卡片挂载时若无封面就 IPC 请求；后端 `video_cover`（`lib.rs:1016-1069`）会 `media::probe` + `media::extract_frame`，两次进程启动，串行过 `cover_gate`。前端限流 2 路（`cover.ts:18-25`），48 张卡最坏要 **48 × ~1.2s / 2 ≈ 29 秒**。已生成过 3310 张（84MB），所以第二次进不再触发——但一旦换源、清理缓存、或新增 2000 条，就会重现。

**改造**

1. **预生成**：扫描收尾后自动排一个后台任务，2 路串行给缺封面的条目生成 **thumb**（320 宽、JPEG q72、`scale=320:-2`），落 `cache/thumb/{id}.jpg`；卡片只用 thumb，详情/播放才用 480 的中帧
2. **视口外不请求**：卡片用 `IntersectionObserver`（rootMargin 200px），进入视口才 `<img src>`；之前是纯色占位 + 容器色
3. **渲染路径里禁止跑进程**：`video_cover` 无缓存时立刻返回 `""` 并抛事件 `cover-ready`，前端收到后替换 —— 绝不阻塞卡片渲染
4. 缓存治理：`cache/` 加 `.cacheindex`（id → 文件名 + 生成时间），每月清理 >90 天未访问的 thumb

#### L3 列表渲染（收益中、风险低）

**证据**：`.video-grid { columns: auto; column-width: 216px }`（`App.css:185`）—— **CSS 多列布局**，任何一项高度变化都会重排整列；且 `videoPage.items` 无限累加（`App.tsx:241-243`），滚到 500 条时 DOM 里 500 个卡片 + 500 个 `<img>`，每次 `setSelected` 都全量 diff。

**改造**

1. 多列布局 → CSS Grid + `content-visibility: auto; contain-intrinsic-size: 216px 200px;`（零依赖，立刻见效，滚动时屏外卡不参与布局与绘制）
2. 首屏 48 → **24**，滚动增量 24（缩短首屏可交互时间）
3. `selected` 从 `Set` 改 `Set` + 卡片 `React.memo`（现在每次勾选 500 张卡全部重渲染）
4. 可选进阶：`@tanstack/react-virtual` 窗口化（只有 40 行可见时才值得上，先不做）

#### L4 播放链路（收益高、风险中）

**证据链**：

- `App.tsx:451-462` `openById` **串行**三次 IPC：`mpvOpen`（无 mpv → 快速 false）→ `mpvClose` → `playback`，每次都要抢全局锁
- `Player.tsx:494` `onTimeUpdate` 里 `setCurrent(...)`：视频播放中每秒触发 ~4 次，**每次都重渲染整个 Player**（9 个比例按钮 + 设置弹层 + 详情抽屉的 props 全部重建）
- `Player.tsx:489-505` `<video src={convertFileSrc(...)}>`：换片时元素重建，`src` 变化后必须重新握手
- `Player.tsx:200` 的 effect 依赖 `[info.video.id, info.start_sec, info.media_path, isMpv, speed]` —— **改倍速也会重跑这段**（`removeEventListener` 再 `play()`）

**改造**

1. **进度不进 React state**：`current` 改为 `useRef` + 直接改 DOM（`seekFill.style.width`、`timeLabel.textContent`），只在 `onPause`/`onSeeked` 时同步一次 state。这一条就能消掉播放中 4 次/秒的全树 diff
2. **换片复用 `<video>`**：key 不用 `id`，`src` 变更前 `v.pause(); v.removeAttribute('src'); v.load();` 再赋新 `src`；`preload="metadata"`，用户点播放才 `preload="auto"`
3. **effect 拆细**：倍速单独一个 effect 只改 `playbackRate`，不重挂 `loadedmetadata`
4. **首帧确定感**：加 `loading` 遮罩（读 `loadeddata` 才撤），大文件显示"正在载入 8.5 GB…"；不要空白黑屏让用户以为死了
5. **openById 并行化**：`Promise.all([mpvOpen, playback])` 会双开 mpv，正确做法是**先读设置判断是否可能走 mpv**（`player_engines` 结果缓存到 localStorage），不可能就直接 `playback`，省两次往返

#### L5 传输层：asset 协议对大文件的代价（收益不确定，需先实测）

**证据**：`tauri.conf.json` 启用 `assetProtocol`，scope 含 `F:/**`；前端用 `convertFileSrc` → `http://asset.localhost/...`。本库最大文件 18.4GB，且已确认存在 **moov 尾置**文件（`FenciZ…mp4`：`ftyp → mdat(11.8G) → moov`）。moov 在尾部的文件，播放器必须先跳到文件末尾读索引，这依赖协议对 `Range` 的稳定支持。

**行动顺序（不要盲目换协议）**

1. 先做 L1–L4（一天内可完成）
2. 做一次**可量化实测**：对 3 个样本（18G / 11.8G / 1G）记录 `loadeddata` 耗时，存 `docs/播放耗时基线.md`
3. 若 1GB 文件也 >3 秒 → 再上自定义协议：`register_asynchronous_uri_scheme_protocol("vvstream", …)`，自己实现 `Range` → `206 Partial Content`，buffer 1MB，CSP 加 `vvstream:`。这条路的收益是"精确 seek、不整文件读"，但要写 100 行 Rust + 处理 `Content-Range` 边界
4. 备选（只对 <2GB 生效）：`ffmpeg -c copy -movflags +faststart` 落到 `cache/faststart/`。18GB 做一次要几分钟，**不作为主方案**

#### L6 解码能力（4K60FPS 的硬上限）

本库存在 `4K60FPS` 全合集（11.8GB）。WebView2 的 `<video>` 走硬件解码，但 4K60 在集显机器上仍会掉帧，这是浏览器内核的天花板，不是代码 bug。

**处置**
1. 探测 `width>=3000 || (高度>=2000) || 码率>25Mbps` → 播放页顶部提示「4K60 建议用 mpv 播放」，一键复制 mpv 参数
2. 设置里 `mpv_path` 已存在，但 `find_mpv` 找不到就静默回落（`mpv.rs:31-49`）。补：设置页「播放内核」卡片显示探测结果（mpv: 未找到 / VLC: 已发现 3.0.21），并提供「指定 mpv 路径」与下载说明
3. 打包内置 mpv（+40MB）：**列为待决策**，不是本次范围

**验收**：1GB mp4 从点击到首帧 <1.5s；播放中滚动鼠标不再掉帧；换片不出现黑屏空窗；勾选/取消勾选卡片无卡顿。

## 六、风险与红线

1. **删除类**：一律先"清单 + 确认"，默认走隔离区（`rename`，同盘瞬时），硬删需输入确认词。压缩包内条目只删记录不动包。
2. **扫描类**：新增源前先 `dry-run` 报"将纳入 N 条视频 / 命中 M 个排除目录"，用户确认再执行。
3. **`F:\Hthings\BENZI` 只读**：它是画匣的库，任何操作不得写入，包括缓存（影匣缓存一律在 `.vault/cache`）。
4. **schema 升级**：v5→v6 前自动 `VACUUM INTO` 备份（`daily_backup` 已有，`db.rs:331`），备份失败则中止升级。
5. **未实测项**：L5 的协议改造收益、4K60 在目标机器上的实际帧率 —— 都标 `NOT TESTED`，等基线测量。
